ENGINEERING
- architecture

# 3. Evidence rule shared by all Wave 2A producers

Every semantic statement generated by a producer must be traceable to one or more exact evidence references, or explicitly marked UNKNOWN / PROPOSED according to mode.

No evidence-free factual claims.

Brownfield allowed labels:

- CURRENT_SYSTEM
- CONFIRMED
- INFERRED
- UNKNOWN

Greenfield allowed labels:

- APPROVED_TARGET
- PROPOSED
- DEFERRED
- UNKNOWN

Foundation refresh may preserve the union already allowed by Shared Core.

A producer MUST NOT:
- convert CURRENT_SYSTEM into APPROVED_TARGET;
- convert code behavior into approved business rules;
- convert inference into CONFIRMED;
- fabricate historical decision rationale;
- invent missing deployment/runtime facts;
- infer a Human decision from repository state.

# 4. Common semantic record

Create a generic producer record or equivalent reusable structure owned under Shared Foundation.

Minimum semantics per statement:

- id
- owner
- topic/category
- statement
- evidence_label
- references
- confidence or inference marker only if needed
- status
- source producer
- open questions / unknowns when applicable

Exact schema design is up to the implementation, but:

- schema_version must be explicit;
- unknown fields fail closed;
- exact refs use Shared Core reference validation;
- owner must be one of BA / ENGINEERING / TEST as appropriate;
- statement IDs are stable within one artifact revision;
- no raw prompt or chain-of-thought field is permitted.

Do not store model reasoning traces.

# 5. domain-discovery

Purpose:
Recover or propose product/domain knowledge without creating a second requirements authority.

Brownfield behavior:
- inspect only explicit evidence supplied by the caller or Foundation inventory references;
- extract candidate terminology, actors, entities, lifecycle/domain concepts and observable rules;
- label implementation-derived behavior CURRENT_SYSTEM;
- label ambiguous semantic interpretation INFERRED;
- unresolved business meaning UNKNOWN;
- only valid project authority plus trusted authority authentication may produce CONFIRMED.

Greenfield behavior:
- organize Human-provided intent/constraints into candidate domain concepts;
- agent-generated business/domain suggestions remain PROPOSED or UNKNOWN;
- no BR/FR is automatically created by this producer.

Required outputs should cover at least:
- glossary candidates
- actors/roles candidates
- domain entities/concepts
- domain lifecycle/state candidates
- business-rule candidates with explicit evidence labels
- gaps/questions
- owner route = BA

Important:
A business-rule candidate from code is NOT a canonical BR.
Promotion into canonical BA artifacts remains BA workflow/Human responsibility.

# 6. architecture-discovery

Purpose:
Recover current architecture or organize target architecture evidence for arc42 sections.

Must support evidence for at least:
- constraints
- context/scope
- solution strategy
- building blocks/modules
- runtime interactions
- deployment topology
- crosscutting concepts
- quality-relevant architecture facts
- risks/technical debt
- architecture decisions inventory

Brownfield rules:
- directory/import/config/container/CI evidence may support CURRENT_SYSTEM;
- architectural pattern names inferred from structure must be INFERRED unless canonical architecture authority confirms them;
- historical rationale is UNKNOWN unless supported by exact decision evidence;
- technology presence is not proof of why it was chosen;
- discovered module boundaries may be CURRENT_SYSTEM, not APPROVED_TARGET.

Greenfield rules:
- target alternatives may be PROPOSED;
- material target choices remain PROPOSED until explicit architecture approval;
- APPROVED_TARGET must reuse Shared Foundation Human approval binding.

Output owner = ENGINEERING.

Do not implement generic codebase scanning outside declared repository roots.
Reuse Foundation inventory and exact refs.

# 7. C4 modeling

C4 is a projection/modeling convention inside Project Foundation architecture, not a new authority layer.

Implement a structured C4 model with at least:

- System Context elements and relationships
- Container elements and relationships
- optional Component elements/relationships
- optional Deployment nodes/instances

Rules:
- Context and Container are the default supported levels.
- Component is optional and should be used only when evidence exists and it adds value.
- Do not force all four C4 levels.
- Every element/relationship must reference architecture evidence or be explicitly PROPOSED/UNKNOWN.
- External actors/systems must be distinguishable from system-owned containers/components.
- IDs must be stable and unique.
- relationships must reference existing IDs.
- no orphan or duplicate IDs.

Structured C4 semantic model may be a candidate architecture artifact.
Rendered Mermaid/PlantUML/Draw.io/SVG/PNG views are DERIVED projections and never become authority merely because rendered.

Wave 2A only needs one deterministic text projection format in addition to the structured model.
Prefer a dependency-light representation already compatible with the repository.
Do not add a heavyweight renderer dependency unless unavoidable.

# 8. ADR management

ADR support must distinguish:

A. Observed current-system decision record
B. Proposed new target decision
C. Human-approved target decision

Historical/current-system ADR recovery:
- may record the observed decision/current technology;
- context may use exact evidence;
- rationale MUST be UNKNOWN when not evidenced;
- alternatives MUST NOT be fabricated;
- status must clearly indicate recovered/current-state nature.

New proposed ADR:
- Context
- Decision proposal
- Consequences
- Alternatives/trade-offs when actually analyzed
- evidence refs
- status PROPOSED

Approved target ADR:
- requires exact Human/Engineering approval binding;
- approval must bind the exact semantic ADR snapshot/revision/hash or an exact enclosing approved Foundation snapshot that explicitly contains the ADR decision;
- agent cannot write APPROVED merely from validator success.

Prefer an ADR/MADR-like durable semantic shape without coupling the framework to one vendor/tool.

Output owner = ENGINEERING.

# 9. test-foundation

Purpose:
Recover or propose project-level test strategy and automation architecture.

Must cover at least:
- test levels/layers used or proposed
- ownership boundaries
- unit/component vs API/integration/E2E/system split
- environment/execution topology
- fixtures/test-data concepts
- quality gates
- observability/evidence expectations
- automation repository role when declared by Project Policy
- gaps/unknowns

Brownfield:
- existing test files/config/CI can establish CURRENT_SYSTEM;
- inferred strategy intent is INFERRED;
- current presence of Playwright/API/etc does not automatically mean an approved future strategy.

Greenfield:
- recommended strategy is PROPOSED until reviewed/accepted;
- this producer must not create feature Test Design/Testcases.

Output owner = TEST.

No Katalon/TEA/Playwright-specific policy may be hard-coded as a framework invariant.

# 10. arc42 projection

Implement deterministic projection from validated Foundation semantic inputs to an arc42 Standard Profile representation.

Requirements:
- all 12 arc42 semantic sections are addressable;
- no requirement for 12 physical files;
- projection may be one Markdown document or a deterministic structured set;
- section content must be assembled only from validated semantic records/manifest refs;
- UNKNOWN/PARTIAL/DEFERRED must remain visible, not silently omitted;
- architecture decisions section links/embeds ADR summaries without inventing rationale;
- glossary may reference BA/domain-owned glossary output;
- quality section may reference Test Foundation output where appropriate;
- business requirements themselves remain outside arc42; section 1 may link/summarize approved product goals without duplicating a requirements authority.

The projection artifact is DERIVED until explicitly promoted/approved through Foundation/project architecture governance.

Do not let generated prose become authority merely because it is in Markdown.

# 11. Cross-producer conflict handling

When owner-specific producers disagree:

- BA-owned domain authority outranks implementation inference for business meaning;
- Engineering current-system evidence may contradict stale architecture docs, but the conflict must be surfaced, not auto-resolved;
- Test strategy recommendations cannot override implementation facts or BA requirements;
- shared exact Project Policy paths across domains remain valid;
- competing claims inside the same domain must remain explicit conflicts.

Produce deterministic conflict records with exact references.

Do not rank sources by model preference.
