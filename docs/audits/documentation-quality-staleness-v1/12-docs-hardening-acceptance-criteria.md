# Future documentation hardening acceptance criteria

This is a future gate definition only. No criterion is declared PASS by this audit.

## Release gate

- 0 unresolved P0 documentation findings.
- 0 unresolved P1 documentation findings.
- 0 current operator pages with incorrect suite/Kit versions, lifecycle states, release status or authority semantics.
- All machine truths originate from manifests, schemas, acceptance contracts, package authority or executable contracts.
- The suite version, each Kit version and prerelease status are discoverable from the primary entry point and agree with machine sources.

## Navigation and task completion

- One clear newcomer entry point exists in every supported documentation language.
- Each target role has one indexed start page and a direct route to prerequisites, inputs, owned outputs, gates, forbidden actions, next transition and troubleshooting.
- The current lifecycle is documented once canonically and all role/task guides link to it.
- Install, upgrade, Doctor, Project Foundation, BA baseline/Handoff, Dev delivery/upstream gap, manual Test, Automation, EXECUTION_READY, execution, Finding routes, defect/fix/retest, VERIFIED and Public Cross-Kit Conformance each have a documented journey with expected result and recovery.
- Every required local navigation link and anchor resolves; external links are either verified or explicitly marked NETWORK_UNVERIFIED.
- No mandatory release gate is reachable only by guessing a file path.

## Authority and readiness

- CONTINUE, ANSWER, validation PASS, generation, Doctor READY, Foundation readiness, Dev READY_FOR_TEST, automation PASS, APPROVED_TESTWARE and EXECUTION_READY are each distinguished from the next Human/Tester decision or product result.
- CANONICAL, DERIVED, RUNTIME, EVIDENCE and HANDOFF_MANIFEST are explained consistently.
- BAREF is described as a technical locator/provenance reference, never canonical business requirement identity.
- Every documented readiness term names its owner, what it proves, what it does not prove, and the allowed next transition.
- READY_TO_MERGE is absent as a framework state unless a future executable contract explicitly introduces it; no prose may imply current merge authority.
- Human identity/semantic authority remains with the trusted host at approval gates.
- Synthetic TEST_ONLY authority is explicitly TEST_ONLY and not_for_production; production Human approval cannot be inferred from fixtures.
- OPTIONAL_DEGRADED is defined separately from Doctor DEGRADED and final suite PASS/FAIL.

## Staleness, language, and history

- Current docs do not present BA 1.x, Dev planned/0.3.x, Test V1/rc.5/rc.6/rc.7/rc.8, STOP_V1, old phases, old branch names or old commands as current defaults.
- Current and historical/legacy content is clearly separated by labels, dates and navigation.
- Historical benchmark evidence is retained without being presented as current guidance; private machine paths/usernames are absent from any newly generated shareable evidence view.
- VI/EN operator pairs agree on state names, commands, versions, warnings, authority, examples and recovery, or explicitly declare NO_COUNTERPART with a supported route.
- Current examples are neutral, minimally realistic and labelled synthetic/illustrative; project-specific names appear only in clearly scoped history/evidence.

## Installation, Doctor and package integrity

- Documented BA, Dev, Test and Project Foundation installation paths are reproducible from a clean checkout on supported operating systems.
- Windows Test package source validation succeeds with the documented Git configuration; package authority, payload digest and installed bytes agree.
- Reinstall/upgrade behavior explains local edits, drift, version checks, recovery and safe stop conditions.
- Doctor READY/DEGRADED/FAIL behavior is described by Kit and suite scope; optional XMind/Excel gaps do not imply core failure or approval.
- Test package authority and digest are generated by repository tooling, never hand-edited.
- Any impacted package has regenerated authority/provenance and pins, an appropriate prerelease version decision, installed acceptance, Doctor validation and package-integrity checks.

## Conformance

- Current Public Cross-Kit Conformance command, Spec Kit v1.0.11 requirement, clean exact-source requirement, output location and expected report fields are documented in the primary release path.
- Fresh-clone Public Cross-Kit Conformance reports PASS on the exact candidate SHA/tree.
- The run reports supported optional projection degradation separately from core Doctor readiness.
- Acceptance applies only to the exact candidate revision; any source/package change invalidates it and requires a fresh run.
- Required impacted kit/package acceptance checks pass; no skips are treated as passes without a documented policy.

These criteria are not an audit PASS declaration and do not authorize package version bumps, semantic changes, merges or release publication.
